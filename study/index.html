01 / ORIENTASI

Apa sebenarnya yang dinilai?

Produk akhirnya sengaja kecil: buat task, ubah status, hapus task, dan lihat riwayat perubahan. Tantangan utamanya ada pada aturan yang selalu benar, termasuk saat request diulang, input salah, atau dua user melihat status berbeda.

01

Fitur

Create, list, update status satu langkah, dan delete task.

02

Jejak perubahan

Setiap perubahan status menyimpan task, actor, status lama dan baru, serta waktu.

03

Invarian

Request yang tidak mengubah status tidak menambah log. Status dan log harus sinkron.

Kalimat kunci

Satu perubahan status yang sah = satu status baru pada task + satu audit log baru. Keduanya berhasil bersama atau tidak berubah sama sekali.

04 / AUDIT LOG

Riwayat yang bisa dipercaya

Log harus bisa menjawab lima hal: task mana, siapa, dari status apa, ke status apa, dan kapan. Setiap entri mewakili satu peristiwa, bukan kondisi terbaru.

10:42 · 01 Jan 2025

john.doe mengubah Prepare invoice dari pending ke in_progress.

Bagaimana log tetap tidak terubah?

  • Tidak ada endpoint untuk edit atau hapus audit log.
  • Operasi update hanya menambahkan entri baru; tidak menulis ulang entri lama.
  • Delete task menyimpan tombstone lewat deletedAt. Riwayat tetap dapat diakses di tab Deleted.
  • Daftar log diurutkan memakai sequence yang meningkat.
Batas jaminan

File JSON masih bisa diubah oleh orang yang mempunyai akses langsung ke file. Jadi “tidak dapat diubah” dijamin oleh jalur aplikasi, belum oleh kontrol database atau tanda tangan kriptografis.

06 / PENYIMPANAN

Mengapa status dan log tetap sinkron?

Implementasi memakai satu file JSON sebagai snapshot. Untuk satu perubahan status, server membaca snapshot, memvalidasi, mengubah status task, menambah log, lalu menulis satu snapshot baru melalui file sementara dan rename atomik.

Baca→Validasi→Ubah task + tambah log→Tulis file sementara→Rename

Bila proses gagal sebelum rename, snapshot lama tetap ada. Bila berhasil, status dan log muncul bersama. Penulisan sinkron membuat request dalam satu proses Node.js berjalan berurutan.

Cukup untuk take-home

Setup singkat, data tetap ada setelah restart, alur mudah diaudit.

Risiko saat skala naik

Dua proses dapat membaca snapshot sama lalu menimpa perubahan satu sama lain. File yang membesar juga memblokir event loop lebih lama.

Langkah refactor pertama: pindahkan penyimpanan ke database transaksional. Update task dan insert log harus berada dalam satu transaksi, dengan version/optimistic locking untuk konflik antar user.

07 / FRONTEND

UI yang menjelaskan perubahan

UI tidak perlu rumit. Yang penting user langsung melihat status saat ini, tindakan berikutnya yang tersedia, actor yang sedang dipakai, dan riwayat perubahan per task.

1

Actor terlihat sebelum update

Dropdown “Acting as” menetapkan identitas yang dikirim saat status berubah.

2

Tombol hanya menuju tahap berikutnya

Ini membuat alur lebih mudah dipahami. Backend tetap memvalidasi karena UI dapat dilewati.

3

Riwayat dibuka di bawah task

User tetap melihat konteks task; log ditampilkan dari paling lama ke paling baru.

4

Deleted tetap dapat ditelusuri

Task keluar dari daftar aktif, tetapi identitas dan audit log masih tersedia.

Pertanyaan saat review

Jika dua browser membuka task yang sama, apa yang terjadi saat keduanya menekan “Move to Pending”? Jelaskan idempotensi, expectedStatus, dan kapan UI perlu memuat ulang data.

09 / DISKUSI TEKNIS

Jawaban yang perlu kamu kuasai

Coba jawab sendiri sebelum membuka penjelasan. Gunakan bahasa kamu sendiri saat interview.

Bagaimana audit log dijaga agar tidak berubah?

Di aplikasi hanya ada operasi tambah dan baca log. Tidak ada endpoint edit/hapus. Soft delete task mempertahankan log. Saat status berubah, task dan log ditulis dalam satu snapshot. Batasnya: pemilik akses file masih dapat mengubah JSON secara langsung.

Bagian mana yang paling berisiko untuk banyak user?

File JSON tidak menyediakan transaksi antar proses. Dua server bisa membaca versi lama yang sama dan update terakhir menimpa update lain. Operasi sinkron juga makin lambat ketika file membesar.

Apa yang paling dahulu direfactor jika sistem membesar?

Ganti FileTaskStore dengan database transaksional. Gabungkan update task dan insert log dalam satu transaksi serta tambahkan version untuk mendeteksi konflik. Setelah itu barulah pagination, auth actor, dan pengujian konkurensi.

Apa trade-off dari soft delete?

Riwayat dan identitas task tetap dapat ditelusuri, tetapi data terus bertambah. Daftar task harus jelas membedakan aktif dan terhapus, dan penyimpanan membutuhkan kebijakan retensi bila dipakai lama.

Bagaimana menjelaskan penggunaan AI?

Sebutkan bagian yang dibantu AI secara spesifik, lalu jelaskan validasi yang benar-benar kamu lakukan: baca ulang aturan domain, jalankan typecheck/build/test, dan periksa kasus batas. Hindari mengklaim test yang belum dijalankan.
